Building a Production-Style Kafka Cluster with Schema Registry

Apache Kafka (3-node KRaft), Confluent Schema Registry, AKHQ, and Python producer/consumer — event streaming with schema governance.

Modern distributed systems rely heavily on event streaming for decoupled communication, scalability, and real-time processing. In this post, I demonstrate a production-style event streaming architecture built using:

  • Apache Kafka — 3-node KRaft cluster (no ZooKeeper)
  • Confluent Schema Registry — centralized schema governance
  • AKHQ — cluster monitoring UI
  • Python Producer — log shipper simulation
  • Python Consumer — log ingestor simulation

This setup demonstrates how distributed durability and schema governance work together to build reliable real-time data pipelines.

Architecture Overview

  Producer (Log Shipper)
          │
          │ 1. Register Schema
          ▼
  Schema Registry
          │
          │ 2. Send (Schema ID + Avro Payload)
          ▼
  Kafka Cluster (3 Brokers - KRaft)
          │
          │ 3. Replicated & Partitioned Storage
          ▼
  Consumer (Log Ingestor)
          │
          │ 4. Fetch Schema by ID → Deserialize

The key idea: Kafka stores bytes, not schemas. Schema Registry ensures structure, validation, and compatibility.

Infrastructure Design

This environment uses a distributed Kafka cluster running in KRaft mode.

  • 3 brokers: kafka1, kafka2, kafka3
  • Controller quorum enabled
  • Replication factor: 3
  • 3 partitions per topic
  • Internal + external listeners configured
  • AKHQ connected internally for monitoring

This design mimics real production deployments used in large-scale microservices systems.

End-to-End Data Flow Explained

1️⃣ Schema Registration

When the producer starts, it sends its Avro schema to Schema Registry. The registry stores it under a subject (e.g., app-logs-value) and assigns a unique Schema ID.

2️⃣ Message Production

Instead of sending the full schema with every message, the producer sends: 

[magic byte][schema ID][serialized avro payload]

Kafka simply stores this as raw bytes inside topic partitions.

3️⃣ Replication & Partitioning

Because replication factor is 3, each message is copied across all brokers. Partitioning allows horizontal scalability, while replication ensures durability and fault tolerance.

4️⃣ Safe Deserialization

The consumer extracts the Schema ID, calls Schema Registry, fetches the correct schema version, and safely deserializes the message into structured data.

Why Schema Registry Is Critical

Without Schema Registry:

  • No schema validation
  • No version management
  • No compatibility enforcement
  • High risk of breaking consumers during deployments

With Schema Registry:

  • Versioned schemas per subject
  • Backward, forward, and full compatibility checks
  • Independent service deployments
  • Safe schema evolution at scale

In large distributed systems, schema governance prevents production outages.

Observability with AKHQ

AKHQ allows you to visualize:

  • Topic configuration
  • Partition leadership
  • Replica distribution
  • Consumer groups & offsets
  • Lag monitoring

This provides operational visibility into cluster health and data flow.

Production Characteristics

  • Modern KRaft architecture (no ZooKeeper)
  • Multi-broker fault tolerance
  • Replication factor greater than 1

This is no longer a simple Kafka demo — it represents a foundational event streaming platform.

Key Takeaways

  • Kafka stores bytes — not schemas.
  • Schema Registry protects your data contracts.
  • Replication ensures durability.
  • Partitioning enables scalability.
  • Consumer groups enable parallel processing.

Event streaming is not just about moving data. It is about maintaining safe, evolving data contracts at scale.

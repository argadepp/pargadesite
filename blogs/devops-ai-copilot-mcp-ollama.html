Building a DevOps AI Copilot with MCP and Ollama

Connecting a Kubernetes cluster to an AI assistant using a Python MCP server, Streamlit, and a locally hosted language model.

Practical POC notes Read-only cluster tools Local model experiments

What if you could ask a question such as “Which pods are running in the dev namespace?” and have an AI assistant call Kubernetes tools to retrieve the live data instead of guessing from general knowledge? That was the idea behind my DevOps AI Copilot proof of concept.

The project combines the Model Context Protocol (MCP) with a Python tool server, a Streamlit chat interface, and a choice of language-model provider. I started with Gemini and then added Ollama so I could experiment with running a smaller model locally or on a small virtual machine.

Scope note: This is a build log describing the components and experiments from the POC, not a claim that the system is production-ready. Commands and architecture below are illustrative where noted; adapt them to your own cluster and repository.

1. Architecture at a glance

The design separates the user interface, language model, MCP tools, and Kubernetes API. The model decides when a tool is useful; the MCP server performs the specific read-only operation and returns structured results for the assistant to explain.

This is intentionally a small architecture: Streamlit provides the chat experience, MCP standardizes tool access, and the Kubernetes client/server side is responsible for retrieving cluster data.

2. What the MCP server can do

The Python MCP server exposes a focused set of Kubernetes and DevOps tools:

ToolPurposeExample question
get_devops_infoReturn general DevOps or environment information exposed by the POC.“What can this assistant help me inspect?”
get_podsRead pod information from the configured cluster.“List pods in the dev namespace.”
get_nodesRead node information and status.“Show me the cluster nodes.”
get_deploymentsInspect deployments in a namespace or the configured scope.“Which deployments are present in default?”

The important point is that the model does not magically know the cluster state. The MCP tool calls fetch the information, and the model helps translate the returned data into a useful answer.

3. Why add Ollama?

The first version used a Streamlit application with Gemini 2.5 Flash. I then added a provider switch so I could compare a hosted model with a model served by Ollama. The initial local default was qwen2.5:3b; the provider client was separated into llm_client.py, with the Streamlit UI retaining the tool-call loop.

  • Gemini 2.5 Flash: convenient for experimenting with a hosted model, subject to network access, credentials, and provider quotas.
  • Ollama + Qwen2.5 3B: a local-model option that avoids sending prompts to a hosted LLM provider, but still requires enough CPU, RAM, and disk.
  • Separate conversation histories: keeping provider histories separate helps avoid mixing context when switching between models.

Local inference can improve control over where prompts are processed, but it is not automatically faster or cheaper in every setup. The available hardware and model size matter.

4. What happened on a small Azure VM?

During a later experiment, I tested a smaller qwen2.5:1.5b model on an Azure VM with 2 vCPUs and roughly 3.8 GiB of RAM, without swap. The Ollama process reached around 195% CPU usage during inference.

Lesson learned: a model can fit on a small VM and still put sustained pressure on its CPU. Check latency, memory, CPU saturation, and concurrency before deciding that a local LLM is suitable for an operational assistant.

For a small proof of concept, reduce model size and concurrency, keep requests short, and measure response time under realistic prompts. For a shared or production service, size the compute deliberately and define what should happen when inference is slow or unavailable.

5. From chat to a DevOps AI Command Center

The next iteration extended the idea beyond a chat window into a lightweight command-center layout. The planned and implemented areas included:

  • A dashboard for pod, node, and deployment health, plus events and restart information.
  • A separate monitoring process that can run independently of an interactive Streamlit session.
  • Namespace selection for monitoring, with the initial scope focused on namespaces such as default and dev.
  • SQLite-backed settings and notification configuration.
  • Telegram and Slack notification configuration, including test-notification workflows.
  • AI-assisted diagnosis to help explain detected signals.

The monitoring workflow is intended to detect and explain issues—not automatically change the cluster. That boundary is deliberate: an assistant can recommend an investigation while an engineer remains responsible for approving operational changes.

6. A sensible safety model

Giving an AI tool access to infrastructure should start with least privilege. For this POC, the Kubernetes MCP tools are read-only. A practical deployment should also:

  • Use a dedicated Kubernetes ServiceAccount and narrowly scoped RBAC permissions.
  • Keep credentials and provider API keys out of source control and logs.
  • Restrict which namespaces and resources can be queried.
  • Validate tool inputs and cap response sizes so large cluster results do not overwhelm the model context.
  • Record tool calls and failures without unnecessarily storing sensitive resource data.
  • Keep remediation separate; require explicit human approval before any future write-capable action.
Security reminder: read-only tools reduce risk but do not remove it. Kubernetes metadata, logs, and event messages can still contain internal names or sensitive operational details.

7. A practical way to reproduce the POC

The exact commands depend on your repository and cluster setup, but a useful build sequence is:

  1. Start with a reachable development cluster such as K3d and verify access using kubectl.
  2. Implement the Python MCP server with one read-only tool first, such as listing pods.
  3. Test each tool directly before connecting an LLM.
  4. Connect the Streamlit UI to the MCP client and implement the tool-call loop.
  5. Add a provider abstraction so Ollama and Gemini can be selected independently.
  6. Test questions where the tool returns data, no results, or an error.
  7. Add monitoring and notifications as a separate workflow, then measure model latency and resource use.

For local Ollama testing, first make sure the model is available in the Ollama instance you are using. For example, the model pull command for the smaller experiment is:

ollama pull qwen2.5:1.5b

That command only downloads the model; it does not install or configure the MCP server, Kubernetes access, or Streamlit application.

8. What I learned

  • MCP gives tools a clear boundary: the model can request specific operations without embedding all infrastructure logic in the prompt.
  • Tool quality matters: predictable, narrow tools are easier to test and safer to operate than a generic command-execution tool.
  • Local models need capacity planning: even a small model can saturate a low-core VM.
  • Monitoring should be decoupled from chat: scheduled detection should not depend on a user keeping a browser tab open.
  • Diagnosis is a safer first step than remediation: make the assistant explain evidence before considering any action-taking capabilities.

Conclusion

This POC helped me explore how MCP, Kubernetes, Streamlit, and Ollama can work together to make operational information easier to query. The most valuable next steps are not simply choosing a bigger model: they are improving tool validation, measuring latency, tightening RBAC, and making alerts reliable.

If you are building a similar DevOps assistant, start with one read-only tool, prove the complete request-and-response flow, and expand only after you can test and observe each component.
